# 21 — Localization

Most of a Music Assistant UI is translated in the frontend. But a large amount of user-facing text is **generated by the server**: config entry labels and descriptions, option titles, provider names and descriptions, error messages, setup-flow steps, task names, and some media item names. None of that can be translated client-side, because the client does not know the strings exist until the server sends them.

`TranslationController` (#4200, extended in #4261 and #4299) solves this by having the server own a translation catalogue and localize its own output during serialization. The design goal is that **no controller or provider has to think about localization**: they attach a translation key to a model, and the value is swapped for the connection's locale on the way out.

---

## The pipeline

Two distinct halves. Authoring and building happen in the repo; resolution happens at runtime.

```
                    ┌─ music_assistant/strings.json                (common.*)
authoring (by hand) ├─ music_assistant/controllers/<c>/strings.json (core.<c>.*)
                    └─ music_assistant/providers/<p>/strings.json   (provider.<p>.*)
                                    │
                                    │  scripts/build_translations.py
                                    ▼
                    music_assistant/translations/en.json    ← flat, sorted, fully-qualified
                                    │
                    lokalise-upload.yml │ push source
                                    ▼
                              Lokalise (translators)
                                    │
                  lokalise-download.yml │ pull translations
                                    ▼
                    music_assistant/translations/<lang>.json
                                    │
                                    │  TranslationController.setup()
                                    ▼
                    in-memory dicts, resolved per connection
```

### Authoring

English source strings live in **nested** `strings.json` files, one per translatable unit:

| File | Key prefix | Count today |
|---|---|---|
| `music_assistant/strings.json` | `common.` | 1 (top-level sections: `config_entries`, `config_categories`, `media`, `player_options`, `errors`, `setup_flow`, `page`) |
| `music_assistant/controllers/<name>/strings.json` | `core.<name>.` | 10 |
| `music_assistant/providers/<domain>/strings.json` | `provider.<domain>.` | 123 |

The `common.` file is where shared strings live — a label like "Username" is authored once rather than 40 times.

### Building

`scripts/build_translations.py` flattens every authoring file into one sorted, fully-qualified `key -> English` map at `music_assistant/translations/en.json` (currently ~2,810 keys). It is standalone by design — no `music_assistant` imports at all — so it runs without the server's import chain and under any models version.

Two behaviours matter:

**Template providers are excluded.** Directories starting with `_` (the `_demo_*` providers) and `test` are skipped, so their placeholder strings never reach Lokalise as translator noise.

**Reference values are resolved and dropped.** A string may be the Home Assistant style token `[%key:owner::path::to::key%]` (with `::` separating dotted segments) instead of literal text. That declares "this key reuses a shared string". The builder validates the target exists as a concrete string and then **omits the referencing key** from the generated catalogue — so Lokalise translates the shared string exactly once, and the server resolves the owner's key at runtime through its owner→common fallback. A reference pointing at a missing target is a hard `ValueError`, so a typo fails the build rather than silently producing an English string in every locale.

`--check` mode compares the rendered output against the committed file and fails if they differ, which is how the pre-commit hook and CI keep `en.json` in sync with the authoring files. The rendering is deterministic (sorted keys, 2-space indent, trailing newline) so the check is stable.

### Translating and downloading

`.github/workflows/lokalise-upload.yml` pushes `en.json` to Lokalise; `lokalise-download.yml` pulls translated languages back as `translations/<lang>.json`, each a flat map with the same fully-qualified keys. Translated files are committed, so a release ships its translations and the server never needs network access to localize.

## Two different "locale" lists

These are easy to conflate and mean different things:

| List | Where | Count | Purpose |
|---|---|---|---|
| **UI locales** | `translations/*.json`, discovered at startup | **32** (31 translated files plus the `en` source) | Which languages the server can localize *its own output* into. Returned by `translations/locales` |
| **Metadata language** | `LOCALES` in `controllers/metadata/constants.py` | **38** | The `CONF_LANGUAGE` option: which language to request from metadata providers, and the locale used for reverse-lookup of localized media names |

The metadata list is larger because asking Spotify for German metadata does not require anyone to have translated MA's own UI into German. Neither list should be hardcoded into documentation — read `translations/` and `controllers/metadata/constants.py`. See [14-metadata.md](14-metadata.md) for the metadata-language setting.

## Runtime resolution

### Loading

`TranslationController.setup()` does three things: discovers `translations/<lang>.json` (filenames only, no parsing), computes `available_locales`, and eagerly loads `en.json` as the final fallback. Translated locales load **lazily on first use**, each behind a per-locale `asyncio.Lock` so concurrent cold loads of the same locale do not both read the file. After that every lookup is an in-memory dict get.

`ensure_locale_loaded(locale)` warms a locale (and its base language) up front. The WebSocket and HTTP layers call it when a connection declares its locale, so no lookup during serialization ever touches disk.

**Setup runs first and sequentially.** In `mass.py` the translations controller is awaited on its own, before the `TaskGroup` that starts the other core controllers concurrently, with the comment *"set up the translations catalog first so it is ready before any object is serialized"*. Every other controller can be serialized, so none of them may start before the catalogue exists. See [00-overview.md](00-overview.md) for the full startup order.

### Key namespaces and the candidate chain

Keys are fully qualified with an owner root: `common.`, `core.<domain>.`, or `provider.<domain>.`. Callers usually pass a **relative** key plus an owner hint, and `_candidate_keys()` expands it into an ordered list, most specific first:

For a relative key with owner `provider.ytmusic`:

1. `provider.ytmusic.<key>` — the owner's own string
2. `provider.<domain>.<key>` — the domain-only form, for a multi-instance owner whose id is `<domain>--<instance>`
3. `common.<key>` — the shared string
4. `<key>` — bare

For an already-qualified key, the key itself plus a `common.` rewrite that drops the owner segment. Additionally, **any candidate ending in `.name` also gets a bare fallback** with `.name` stripped, which is what lets an authoring file write either `foo.name` or just `foo`.

That fallback ladder is what makes the build-time reference mechanism work: an owner declaring `[%key:common::settings::username::label%]` has its key omitted from the catalogue entirely, and the runtime finds the shared `common.settings.username.label` on candidate 3.

Each candidate is probed across locales in turn — the requested locale (normalized, `-` → `_`), then its base language (`de_DE` → `de`), then the English source. `get_translation()` returns `None` when nothing matches, and **never raises**, so the caller keeps whatever English value it already had rather than displaying a raw key.

### `translation_owner`

Both base classes expose the namespace their strings resolve under:

| Class | Property |
|---|---|
| `CoreController` | `translation_owner` → `f"core.{self.domain}"` |
| `Provider` | `translation_owner` → `f"provider.{self.domain}"` |

Anything carrying a relative translation key passes this alongside it so the resolver knows which owner prefix to try. `ProviderError` and its subclasses carry `translation_key`, `translation_args`, and `translation_owner` together, which is how a provider-raised error arrives at the client already localized — see [02-configuration.md](02-configuration.md) and [15-provider-lifecycle.md](15-provider-lifecycle.md).

`BackgroundTask.translation_owner` is stamped by the tasks controller and marked `serialize="omit"`: it is resolution machinery, not data the client needs. See [20-background-tasks.md](20-background-tasks.md#the-task-model).

### Resolution during serialization

The mechanism is a `ContextVar` in the models package, `TRANSLATION_RESOLVER`, plus a `resolve_translation()` helper that models call from their `__post_serialize__` hooks.

The server binds the resolver for the duration of each outbound serialization:

| Transport | Where |
|---|---|
| WebSocket | `_send_message` (in an executor, with `contextvars.copy_context()`) and `_send_message_sync` (inline), both bound to the connection's locale |
| HTTP | `_localized_json_response`, bound to the locale derived from `Accept-Language` |

Three properties fall out of doing it this way:

**Models localize themselves.** A `ConfigEntry`, `BackgroundTask`, or media item swaps its own `label`/`name`/`title`/`description` for the localized string inside `__post_serialize__`. No controller passes a locale anywhere.

**Internal serialization is untouched.** `translations_active()` returns whether a resolver is bound. Plain `to_dict()` calls used for caching, item mappings, and config storage have no resolver, so they keep the English source *and* keep the `translation_key` machinery in the output — which is essential, because a cached object must still be localizable when it is later served to a different connection with a different locale. Localized API output strips the machinery instead.

**Failures are invisible.** `resolve_translation()` catches every exception and returns `None`, with the reasoning in the code: resolution must never break serialization. A broken catalogue degrades to English, not to a 500.

### Locale selection per connection

| Path | How the locale is chosen |
|---|---|
| WebSocket | An optional `locale` argument on the `auth` command, or the `translations/set_locale` pre-dispatch command at any time. Stored on the connection handler |
| HTTP | Per request from `Accept-Language` — highest-priority tag, `q=` factors dropped, `None` when absent |

`translations/set_locale` is one of only two commands handled *before* the command registry is consulted, precisely because it mutates connection state rather than invoking a controller. See [12-webserver-api.md](12-webserver-api.md#special-pre-dispatch-commands).

The only API command is `translations/locales`, which returns the sorted `available_locales`.

### Reverse lookup: finding localized media names

One place where translation runs *backwards*. Genre and playlist names for built-in content are themselves translatable, so a user searching for a genre by the name they see on screen would find nothing — the library stores the canonical English `search_name`.

`reverse_lookup_media_names(query)` closes that gap: it scans the configured metadata language's bundle for `*.media.genre.*` / `*.media.playlist.*` keys ending in `.name` whose localized value contains the normalized query, and returns the **English** source strings for the matches. A text search that comes back empty can retry against those.

Three deliberate limits: only genres and playlists are considered (the searchable library media types — browse and recommendation folder titles are display-only and never library items); the locale is the metadata controller's `CONF_LANGUAGE` rather than the connection locale, since it doubles as the fallback search locale; and an English, unknown, or untranslatable language returns an empty set, because a literal search already covers English. See [08-media-library.md](08-media-library.md#search).

## Adding a translatable string

1. Add the English text to the relevant `strings.json` — the provider's or controller's own file, or `music_assistant/strings.json` if it is genuinely shared.
2. To reuse an existing shared string instead, set the value to `[%key:common::path::to::key%]`.
3. Run `uv run -m scripts.build_translations` and commit the regenerated `translations/en.json`.
4. Reference the key from the model — a `ConfigEntry`'s `translation_key`, an error's `translation_key` plus `translation_owner`, and so on. Relative keys are resolved against the owner automatically.

The `check_translatable_labels` pre-commit hook enforces that user-facing labels are translatable rather than hardcoded English, and the `build_translations_source --check` hook keeps `en.json` in sync.
